01 / Контекст

Долгая задача.
Понятный статус.

QA-инженер описывает проверку и выбирает тип теста. В контракте запроса предусмотрены manual, api и ui, а также приоритет и контекст задачи.

API возвращает идентификатор фоновой задачи. Её выполнение, прогресс и сохранённые файлы представлены отдельными частями системы.

Технические пояснения относятся к командной кодовой базе из моего форка. Все ссылки в разборе закреплены на одной версии исходников.

03 / Обратная связь

Видно, что
происходит.

Четыре состояния из обработчика статуса. Это описание контракта API по коду — состояние реальной задачи здесь не отображается.

pendingОжидает выполнения
Для состояния Celery PENDING обработчик проверяет наличие записи задачи в базе.
in_progressВыполняется
PROGRESS преобразуется в ответ с текущим шагом, общим числом шагов, процентом и сообщением.
completedРезультат готов
При SUCCESS ответ содержит сериализованный результат и прогресс 100%.
failedВозникла ошибка
При FAILURE обработчик извлекает описание ошибки и возвращает его в поле error.

04 / Результаты

Статус задачи.
Файлы отдельно.

В исходниках разделены результат Celery, запись истории и содержимое сгенерированных файлов.

TaskRecordИстория задачи
Хранит идентификатор, описание, тип теста, приоритет и статус. Отдельные поля предусмотрены для ошибки и сообщения о прогрессе.
TaskArtifactСодержимое файлов
Связан с записью задачи. Модель содержит имя файла, описание и текст результата; при чтении статуса обработчик пытается сохранить полученные артефакты.
Чтение файловОтдельный метод Core Agent

GET /api/v1/tasks/{task_id}/artifacts возвращает сохранённые файлы из базы, обращаясь к TaskRecord и TaskArtifact.
